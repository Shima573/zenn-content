## はじめに

前回はMVCについて改めて学習し、Model・View・Controllerがそれぞれどのような役割を持っているのかを整理しました。

その中で、ブラウザから送られたリクエストがルーティングを経由してControllerに届く、という流れが出てきました。

今回はその部分をさらに掘り下げ、HTTPとは何か、RailsがどのようにリクエストをControllerへ振り分けているのかについて、自分の個人開発アプリ「やまッチ」を例に整理します。

## HTTPとは

HTTP（Hypertext Transfer Protocol）とは、WebブラウザなどのクライアントとWebサーバーの間で、文字や画像などのWeb情報をやりとりするための通信ルール（プロトコル）です。

### 「通信ルール」って何？

人間同士でも、好き勝手な形式で情報を送ったら相手が理解できません。

そのためHTTPでは、クライアントとサーバーが以下のような共通の形式に従って通信を行います。

- 「こういう形式で要求を送ろう（リクエスト）」
- 「こういう形式で結果を返そう（レスポンス）」

HTTP通信は、クライアントからサーバーへ「リクエスト」を送り、それに対してサーバーが「レスポンス」を返す一往復のやり取りが基本となります。

### リクエストとレスポンス

例えば、ブラウザから「やまッチ」の登山プラン詳細画面にアクセスした場合を考えてみます。

ブラウザからサーバーへ「このページを表示したい」というリクエストが送られ、サーバー側で必要な処理を行ったあと、その結果がレスポンスとしてブラウザへ返されます。

## HTTPメソッド

HTTPメソッドとは、HTTPリクエストで「対象に対して何をしたいのか」を表すものです。

例えば、データを取得したい場合は`GET`、新しく作成したい場合は`POST`など、目的に応じて使用するHTTPメソッドが異なります。

| やりたいこと | HTTPメソッド | 例 |
| --- | --- | --- |
| プラン一覧を見る | GET | `GET /plans` |
| プラン詳細を見る | GET | `GET /plans/1` |
| 新規作成する | POST | `POST /plans` |
| 既存プランを更新する | PATCH | `PATCH /plans/1` |
| プランを削除する | DELETE | `DELETE /plans/1` |

### GET

サーバーからデータを取得するときに使用します。

例えば、登山プランの詳細画面を表示する場合は`GET`を使用します。

```text
GET /plans/1
```

### POST

`POST`は、サーバーへデータを送信し、新しいリソースを作成するときなどに使用します。

例えば、新しい登山プランを作成する場合は、基本的には次のようなリクエストになります。

```text
POST /plans
```

#### やまッチの場合

やまッチでは、どの山についての登山プランなのかを特定する必要があるため、Planの作成ルートをMountainにネストしています。

そのため、実際には次のようなルートになっています。

```text
POST /mountains/:mountain_id/plans → plans#create
```

ネストについては後ほど詳しく整理します。

### PATCH・PUT

既存のデータを更新するときに使用します。

`PATCH`は一部を変更する更新、`PUT`はリソース全体を置き換える更新という違いがあります。

Railsでは、`resources`によって生成されるルーティングでは、どちらも`update`アクションに割り当てられます。

```text
PATCH /plans/1 → plans#update
PUT   /plans/1 → plans#update
```

### DELETE

既存のデータを削除するときに使用します。

例えば、作成済みの登山プランを削除する場合に使用します。

```text
DELETE /plans/1 → plans#destroy
```

### じゃあ、いつHTTPメソッドを決めるの？

考え方としては、機能を設計するときに「この機能は何をするのか」を考えます。

```text
見る？
↓
GET

新しく作る？
↓
POST

変更する？
↓
PATCH

削除する？
↓
DELETE
```

そしてRailsでは、「どのHTTPメソッドとパスを、どのController#Actionに対応させるのか」をルーティングとして定義します。

## HTTPとHTTPSの違い

WebサイトのURLを見ると、`http://`ではなく`https://`となっていることが多くあります。

HTTPS（Hypertext Transfer Protocol Secure）は、HTTPによる通信をTLSによって暗号化して安全に行う仕組みです。

例えば、

`http://example.com`

と

`https://example.com`

では、HTTPSの方は通信内容が暗号化されます。

ログイン情報やフォームに入力した内容などを、通信途中で第三者に読み取られたり改ざんされたりするリスクを抑えることができます。

今回の「やまッチ」も、

`https://yamatchapp.com`

となっているため、HTTPSで通信しています。

ただし、HTTPメソッドやリクエスト・レスポンス、Railsのルーティングといった今回学習する基本的な考え方はHTTPSでも同じです。

## URLとパスの関係

URL（Uniform Resource Locator）とは、Web上のリソースの場所を示すものです。

パス（Path）は、そのURLの中で特定のリソースや場所を示す部分です。

例えば、やまッチのURLを見てみます。

```text
https://yamatchapp.com/plans/1
```

それぞれ、

```text
https://
→ プロトコル

yamatchapp.com
→ ホスト名

/plans/1
→ パス
```

となります。

### HTTPメソッドと組み合わせる

先ほど学んだHTTPメソッドがここでつながります。

例えば、ブラウザから登山プランの詳細を表示するために、

```text
GET /plans/1
```

というリクエストが送られたとします。

ここでは、

- `GET`：HTTPメソッド
- `/plans/1`：パス

を表しています。

Railsでは、この「HTTPメソッド + パス」の組み合わせをルーティングと照合し、どのControllerのどのActionで処理するのかを決めます。

## Railsのルーティングとは

Railsのルーティングとは、受け取ったHTTPリクエストを、どのControllerのどのActionで処理するのかを決める仕組みです。

例えば、

```text
GET /plans/1
```

というリクエストが送られてきたときに、

```text
PlansController#show
```

で処理する、といった対応関係を定めます。

### routes.rbの役割

Railsでは、ルーティングを主に次のファイルに定義します。

```text
config/routes.rb
```

例えば、

```ruby
get "/plans/:id", to: "plans#show"
```

というルートがあったとします。

これを分解すると、

```text
get
↓
HTTPメソッド

"/plans/:id"
↓
パス

"plans#show"
↓
PlansControllerのshowアクション
```

という意味です。

ここで区別しておきたいのが、`routes.rb`自身がControllerの処理を行っているわけではないということです。

例えば、

```ruby
@plan = Plan.find(params[:id])
```

のようなデータを取得する処理を`routes.rb`が行うわけではありません。

役割としては、

```text
routes.rb

「このリクエストの行き先はPlansController#showです」

                  ↓

PlansController#show

「詳細表示に必要な処理をします」
```

というように、リクエストの行き先を決めるところです。

これはMVCの記事で整理した「責務を分ける」という考え方にもつながります。

## resourcesとは

Railsでは、一般的なCRUD操作に対応するルーティングをまとめて定義するために`resources`を使用できます。

その前に、まず`resource`とCRUDが何を意味するのか整理します。

### そもそもresourceって何？

ここでいうリソース（resource）は、Webアプリで扱う対象となるデータや概念くらいに考えています。

やまッチなら、

```text
Mountain → 山
Plan     → 登山プラン
Favorite → お気に入り
```

などがリソースになります。

例えばPlanに対して、

```text
一覧を見る
新規作成する
詳細を見る
編集する
更新する
削除する
```

といった操作を行います。

### CRUDとは？

CRUDとは、データに対する基本的な4つの操作を表したものです。

```text
Create → 作成
Read   → 取得・表示
Update → 更新
Delete → 削除
```

例えばPlanで考えると、

- 新しいPlanを作成する → Create
- Planの一覧や詳細を見る → Read
- 作成済みのPlanを更新する → Update
- Planを削除する → Delete

となります。

Railsでは、このようなリソースに対する一般的なCRUD操作を、一定の規約に沿ってルーティングするために`resources`を使います。

### resources :plans

ルーティングは一つずつ、

```ruby
get "/plans", ...
get "/plans/:id", ...
post "/plans", ...
patch "/plans/:id", ...
delete "/plans/:id", ...
```

のように定義することもできます。

しかしRailsでは、

```ruby
resources :plans
```

と書くことで、Planに対する基本的なルーティングをまとめて定義できます。

`resources`には、単にコードを短くするだけではなく、Railsの規約に沿ったルーティングをまとめて定義できるという利点があります。

### resourcesでは複数形のシンボルを使う

`resources :plans`の`:plans`にもRailsの規約があります。

`resources`では、基本的にリソース名を**複数形のシンボル**で指定します。

例えば、

```ruby
resources :plans
resources :mountains
resources :favorites
```

のように記述します。

`:plans`の先頭にある`:`は、Rubyのシンボルを表しています。

また、`Plan`というリソースに対して、`plan`ではなく複数形の`plans`を指定します。

### resourcesで生成される7つのルート

`resources :plans`を定義すると、基本となる7つのアクションに対応するルートが生成されます。

| HTTPメソッド | パス | Controller#Action | 目的 |
| --- | --- | --- | --- |
| GET | `/plans` | `plans#index` | 一覧 |
| GET | `/plans/new` | `plans#new` | 新規作成画面 |
| POST | `/plans` | `plans#create` | 作成 |
| GET | `/plans/:id` | `plans#show` | 詳細 |
| GET | `/plans/:id/edit` | `plans#edit` | 編集画面 |
| PATCH / PUT | `/plans/:id` | `plans#update` | 更新 |
| DELETE | `/plans/:id` | `plans#destroy` | 削除 |

CRUDは4つの基本操作ですが、Railsでは`new`や`edit`のような入力画面を表示するためのActionもあるため、`resources`では基本的に7つのActionに対応するルートが生成されます。

### RESTfulなルーティング

`resources`によって生成されるルーティングは、REST（REpresentational State Transfer）というWebの設計思想を意識したものになっています。

例えばPlanというリソースに対して、

- `GET`で取得する
- `POST`で作成する
- `PATCH`で更新する
- `DELETE`で削除する

というように、リソースとHTTPメソッドを組み合わせて操作を表現します。

Railsでは`resources`を使うことで、このようなRESTfulなルーティングを規約に沿ってまとめて定義できます。

今回はHTTPとRailsのルーティングの基本を整理することが目的なので、RESTについての詳しい説明は省略します。

### only:で必要なルートだけ定義する

`resources :plans`を定義すると、基本となる7つのアクションに対応するルートが生成されます。

```text
index
show
new
create
edit
update
destroy
```

しかし、必ずしもすべてのルートが必要になるとは限りません。

そこで使えるのが`only:`です。

```ruby
resources :plans, only: %i[index show edit update destroy]
```

これは、

「Planについては、index・show・edit・update・destroyのルートだけ作ってください」

という意味です。

そのため、この場合は`new`と`create`のルートは生成されません。

逆に`except:`を使って、

```ruby
resources :plans, except: %i[new create]
```

と書くこともできます。

こちらは「newとcreate以外」という指定です。

必要なルートだけを定義することで、そのリソースに対してどのような操作ができるのかも分かりやすくなります。

### ネストとは

次に、やまッチで使用しているネストについて整理します。

例えば、

```ruby
resources :mountains do
  resources :plans, only: %i[new create]
end
```

のように、ある`resources`の中に別の`resources`を書くことをネスト（入れ子）といいます。

構造として見ると、

```text
mountains
└── plans
```

となります。

こうすることで、「Mountainに紐づくPlan」という関係をURLでも表現できます。

例えば、次のようなルートが生成されます。

```text
GET  /mountains/:mountain_id/plans/new
POST /mountains/:mountain_id/plans
```

`/mountains/5/plans/new`にアクセスした場合、`:mountain_id`には`5`が入り、Controllerでは、

```ruby
params[:mountain_id]
```

として取得できます。

これによって、「どのMountainについてPlanを作成するのか」を特定できます。

#### なぜPlanをMountainにネストするのか

やまッチでは、新しい登山プランを作るときに、

「どの山についての登山プランなのか？」

という情報が必要です。

そのため、

```text
/plans/new
```

ではなく、

```text
/mountains/5/plans/new
```

とすることで、

```text
/mountains/5
     ↑
MountainのID

/plans/new
     ↑
その山のPlanを新規作成
```

という関係をURLで表現しています。

一方、すでに作成されたPlanについては、Plan自身のIDで対象を特定できます。

そのため、やまッチでは`new`と`create`だけをMountainにネストし、それ以外のPlan操作はPlan単体のルートとしています。

実際の`config/routes.rb`では、次のように定義しています。

```ruby
resources :mountains do
  resources :plans, only: %i[new create]
end

resources :plans, only: %i[index show edit update destroy]
```
## rails routesの読み方

定義されているルーティングは、`rails routes`で確認できます。

やまッチでPlanに関するルートを確認すると、次のようになっています。

```text
Prefix            Verb    URI Pattern                                  Controller#Action

mountain_plans    POST    /mountains/:mountain_id/plans(.:format)      plans#create
new_mountain_plan GET     /mountains/:mountain_id/plans/new(.:format)  plans#new
plans             GET     /plans(.:format)                             plans#index
edit_plan         GET     /plans/:id/edit(.:format)                    plans#edit
plan              GET     /plans/:id(.:format)                         plans#show
                  PATCH   /plans/:id(.:format)                         plans#update
                  PUT     /plans/:id(.:format)                         plans#update
                  DELETE  /plans/:id(.:format)                         plans#destroy
```

例えば、次のルートを見てみます。

```text
plan  GET  /plans/:id(.:format)  plans#show
```

これは、

- `plan`：Prefix
- `GET`：HTTPメソッド
- `/plans/:id`：一致するパス
- `plans#show`：処理を担当するController#Action

という意味です。

例えばブラウザから、

```text
GET /plans/5
```

というリクエストが送られた場合、`:id`には`5`が入り、このルートに一致します。

※`(.:format)`はレスポンスの形式に関係する部分ですが、今回はルーティングの基本に絞るため、詳しい説明は省略します。

### Prefix

Prefixは、名前付きルートの元になる名前です。

例えば、

```text
plan
```

というPrefixがある場合、Railsでは、

```ruby
plan_path(@plan)
```

のようなパスヘルパーを使用できます。

ほかにも、

```text
edit_plan
```

であれば、

```ruby
edit_plan_path(@plan)
```

のように使用できます。

Prefixによって、ViewやControllerなどからURLを直接文字列で書かず、パスヘルパーを使って扱うことができます。

### Verb

HTTPメソッドを表します。

前半で確認した`GET`、`POST`、`PATCH`、`PUT`、`DELETE`などが表示されます。

例えば、

```text
GET /plans/:id
```

と、

```text
PATCH /plans/:id
```

ではパスは同じですが、HTTPメソッドが異なります。

そのため、

```text
GET   /plans/:id → plans#show
PATCH /plans/:id → plans#update
```

のように、異なるActionへ振り分けることができます。

### URI Pattern

どのようなパスに一致するルートなのかを表します。

例えば、

```text
/plans/:id
```

の`:id`は固定された文字ではなく、動的に変わる部分です。

```text
/plans/5
```

というパスなら、`:id`には`5`が入ります。

Controllerでは、

```ruby
params[:id]
```

として取得できます。

また、やまッチのネストしたルートでは、

```text
/mountains/:mountain_id/plans/new
```

となっており、`:mountain_id`から対象となるMountainのIDを取得できます。

### Controller#Action

リクエストをどのControllerのどのActionで処理するのかを表します。

例えば、

```text
plans#show
```

であれば、

```text
PlansControllerのshowアクション
```

で処理することを意味します。

## ブラウザからControllerに届くまで

ここまで学習した内容を使って、ブラウザからControllerにリクエストが届くまでの流れを整理します。

例えば、ブラウザから、

```text
https://yamatchapp.com/plans/5
```

にアクセスしたとします。

まずブラウザから、次のHTTPリクエストが送られます。

```text
GET /plans/5
```

Railsは、HTTPメソッドとパスの組み合わせをルーティングと照合します。

`rails routes`で確認したルートには、

```text
plan  GET  /plans/:id  plans#show
```

があります。

今回送られてきた、

```text
GET /plans/5
```

は、

```text
GET /plans/:id
```

に一致します。

このとき、

```text
:id = 5
```

となります。

ルーティングによって処理先が、

```text
plans#show
```

と決まり、`PlansController`の`show`アクションへ処理が渡されます。

Controllerでは、

```ruby
params[:id]
```

から`5`を取得できます。

流れをまとめると、

![ブラウザからRails Controllerまでの流れ](/images/rails-routing-flow.png)

となります。

ここからControllerがModelを利用して必要なデータを取得し、Viewによる画面表示につなげていきます。

この先の流れは、前回整理したMVCの処理につながります。


## まとめ

今回は、HTTPとRailsのルーティングについて改めて整理しました。

HTTPでは、クライアントからサーバーへリクエストを送り、サーバーからレスポンスを返すことで通信を行います。

そしてリクエストには、

- `GET`、`POST`、`PATCH`、`DELETE`などのHTTPメソッド
- `/plans/5`などのパス

があり、Railsは「HTTPメソッド + パス」の組み合わせをルーティングと照合します。

Railsでは`config/routes.rb`にルーティングを定義し、`resources`を使うことで、CRUDに対応したルートを規約に沿ってまとめて定義できます。

今回、自分のアプリのルーティングを実際に確認したことで、

```text
ブラウザ
↓
HTTPリクエスト
↓
ルーティング
↓
Controller#Action
```

という流れが以前より具体的に理解できました。

特に、同じ`/plans/:id`というパスでも、`GET`なら`show`、`PATCH`なら`update`というように、HTTPメソッドとパスの組み合わせによって処理先が決まることが理解できました。

今後Railsのコードを読むときも、Controllerだけを見るのではなく、

「どのHTTPリクエストが、どのルートに一致して、このActionに届いているのか」

という流れを意識して確認していきたいと思います。
