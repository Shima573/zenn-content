# はじめに

個人開発した登山サポートアプリ「やまッチ」では、開発環境の構築にDockerを使用しています。

これまでは `docker compose up` などのコマンドを使って開発を進めていましたが、
Dockerが内部で何をしているのか、イメージやコンテナ、Volumeがどのような役割を持っているのかまでは、十分に理解できていませんでした。

そこで今回は、Dockerの基本的な仕組みを整理しながら、自作アプリで使用している `Dockerfile.dev` と `compose.yaml` の内容を確認していきます。

# 1. Dockerとは

Dockerとは、アプリケーションを動かすために必要な環境を、コンテナという単位で管理・実行するための技術です。

例えば、Railsアプリを動かすためには、RubyやPostgreSQL、Node.js、Yarnなどが必要になります。

Dockerを使用しない場合、これらを自分のPCに直接インストールし、バージョンや設定を管理する必要があります。

一方、Dockerを使用すると、必要な実行環境をコンテナとして用意できます。

また、環境の設定をファイルで管理できるため、別のPCでも同じような開発環境を再現しやすくなります。

![開発環境比較](/images/Dockerあり・なし開発環境比較.png)

## Dockerを使うメリット

- 開発環境を再現しやすい
- PCに直接インストールするソフトウェアを減らせる
- アプリごとに異なるバージョンの環境を用意できる
- 複数のサービスを分けて管理できる

ただし、Dockerを使用すれば必ず完全に同じ環境になるわけではなく、バージョンや設定を適切に管理する必要があります。

# 2. Dockerの基本用語

Dockerを理解するうえで、まず覚えておきたい用語があります。

| 用語 | 役割 |
| --- | --- |
| イメージ | コンテナを作るためのひな形 |
| コンテナ | イメージから作られる実行環境 |
| Dockerfile | イメージの作り方を記述するファイル |
| Docker Compose | 複数のサービスをまとめて管理する仕組み |
| Volume | コンテナとは別にデータを保持する仕組み |

## イメージとコンテナの違い

最初に混同していたのが、イメージとコンテナの違いです。

**イメージは実行環境のひな形で、コンテナはそのイメージから作られる実行環境**です。

例えば、料理に置き換えると次のようなイメージになります。

- Dockerfile：レシピ
- イメージ：レシピに従って準備された調理セット
- コンテナ：そのセットを使って実際に調理する場所

Dockerfileをもとにイメージを作ることを「ビルド」と呼びます。

また、1つのイメージから複数のコンテナを作ることもできます。

# 3. やまッチのDocker構成

やまッチの開発環境では、主に2つのサービスを使用しています。

| サービス | 役割 |
| --- | --- |
| web | Ruby on Railsを動かす |
| db | PostgreSQLを動かす |

この2つを `compose.yaml` で定義しています。

また、Rails側のイメージを作成するために `Dockerfile.dev` を使用しています。

それぞれの役割は次のとおりです。

- `Dockerfile.dev`：Railsを動かす環境の作り方を定義する
- `compose.yaml`：webとdbの構成や起動方法を定義する

つまり、**Dockerfileはイメージの作り方、Docker Composeは複数のサービスの管理**を担当しています。

# 4. Dockerfile.devの内容を確認する

ここからは、実際のコードを確認します。

## FROM：ベースとなるイメージ

```dockerfile
FROM ruby:3.3.6
```

`FROM` は、イメージを作成する際の土台を指定します。

今回はRuby 3.3.6のイメージを使用しています。

Rubyを一からインストールするのではなく、すでにRubyが用意されたイメージを利用しています。

## ENV：環境変数の設定

```dockerfile
ENV LANG C.UTF-8
ENV TZ Asia/Tokyo
```

`ENV` は、イメージやコンテナ内で使用する環境変数を設定する命令です。

- `LANG`：文字の扱いに関するロケール設定
- `TZ`：タイムゾーンの設定

今回は文字コードに関する設定と、日本時間を指定しています。

## RUN：必要なソフトウェアのインストール

```dockerfile
RUN apt-get update -qq \
&& apt-get install -y ca-certificates curl gnupg
```

実際のファイルでは、この後にNode.jsとYarnのリポジトリを登録する処理が続いています。

さらに、以下のコマンドで必要なパッケージをインストールしています。

```dockerfile
RUN apt-get update -qq && apt-get install -y build-essential libpq-dev nodejs yarn vim
```

ここで重要なのが `RUN` の実行タイミングです。

**RUNはイメージをビルドするときに実行される命令**です。

コンテナを起動するたびに、これらのインストール処理が実行されるわけではありません。

なお、Yarnのリポジトリ登録で使用している `apt-key` は非推奨となっているため、今後修正したい部分です。

## WORKDIR：作業ディレクトリの指定

```dockerfile
RUN mkdir /myapp
WORKDIR /myapp
```

`RUN mkdir` でディレクトリを作成し、`WORKDIR` で作業ディレクトリを指定しています。

`/myapp` はMac上のディレクトリではなく、Dockerイメージ内のパスです。

## COPY：ファイルのコピー

```dockerfile
RUN gem install bundler
COPY . /myapp
```

`gem install bundler` でBundlerをインストールしています。

`COPY` は、ビルド時にファイルをイメージへコピーする命令です。

今回はビルドコンテキスト内のファイルを `/myapp` にコピーしています。ただし、`.dockerignore` で除外したものはコピーされません。

# 5. compose.yamlの内容を確認する

次に、Docker Composeの設定を確認します。

## services：サービスの定義

```yaml
services:
  db:
    image: postgres
    restart: always
```

`db` というサービスを定義し、PostgreSQLのイメージを使用しています。
restart: always は、コンテナが停止した場合の再起動方針を指定する設定です。

一方、webは次のように定義しています。

```yaml
web:
  build:
    context: .
    dockerfile: Dockerfile.dev
```

こちらは `Dockerfile.dev` を使用してイメージをビルドする設定です。

つまり、dbは既存のイメージを利用し、webはDockerfileからイメージを作成しています。

なお、`image: postgres` にはバージョンが指定されていないため、環境の再現性を考えると、バージョンの固定も検討したいところです。

## command：起動時に実行する処理

```yaml
command: bash -c "yarn install && bundle install && bundle exec rails db:prepare && rm -f tmp/pids/server.pid && ./bin/dev"
```

これは、webコンテナの起動時に実行するコマンドです。

| コマンド | 役割 |
| --- | --- |
| yarn install | JavaScript関連のパッケージを用意する |
| bundle install | 必要なGemを用意する |
| rails db:prepare | DBを利用できるように準備する |
| rm -f tmp/pids/server.pid | 古いPIDファイルを削除する |
| ./bin/dev | 開発用のプロセスを起動する |

`&&` は、前のコマンドが成功した場合に次のコマンドを実行するという意味です。

### RUNとcommandの違い

| | RUN | command |
| --- | --- | --- |
| 記述場所 | Dockerfile.dev | compose.yaml |
| 実行タイミング | ビルド時 | コンテナ起動時 |
| 目的 | 実行環境の構築 | アプリの起動など |

これまで意識していませんでしたが、イメージを作る処理とコンテナを起動する処理は別のものだと分かりました。

# 6. Volumeとは

Volumeは、コンテナとは別にデータを保持するための仕組みです。

コンテナを削除すると、コンテナ固有の書き込み領域に保存されていたデータは失われます。

そこで、保持しておきたいデータをVolumeに保存します。

## 名前付きVolume

やまッチでは、以下の名前付きVolumeを定義しています。

```yaml
volumes:
  bundle_data:
  postgresql_data:
  node_modules:
```

名前付きVolumeとは、Dockerが管理するデータの保存領域に名前を付けたものです。

| Volume | 用途 |
| --- | --- |
| bundle_data | Gemの保存 |
| postgresql_data | DBデータの保存 |
| node_modules | JavaScript関連パッケージの保存 |

例えば、dbサービスには以下の記述があります。

```yaml
volumes:
  - postgresql_data:/var/lib/postgresql
```

左側の `postgresql_data` がVolume名、右側の `/var/lib/postgresql` がコンテナ内のマウント先です。

これにより、コンテナを削除して作り直しても、Volumeが残っていればデータを再利用できます。

ただし、実際のPostgreSQLのデータ保存先はイメージのバージョンや設定によって異なるため、マウント先が正しいかは確認が必要です。

## バインドマウントとの違い

やまッチでは次の設定も使用しています。

```yaml
volumes:
  - .:/myapp
```

これは名前付きVolumeではなく、バインドマウントです。

Mac側のプロジェクトディレクトリを、コンテナの `/myapp` にマウントしています。

| | 名前付きVolume | バインドマウント |
| --- | --- | --- |
| 保存先 | Dockerが管理 | Mac側の指定したパス |
| 指定例 | bundle_data:/usr/local/bundle | .:/myapp |
| 主な用途 | DBやGemのデータ保持 | ソースコードの共有 |

RailsのコードはMac側で編集し、GemやDBのデータはDocker側で管理する、という使い分けをしています。

# 7. depends_onとhealthcheck

dbには、次の設定があります。

```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U postgres"]
  interval: 10s
  timeout: 5s
  retries: 5
```

`pg_isready` は、PostgreSQLが接続を受け付けられる状態かを確認するコマンドです。

そしてweb側には次の設定があります。

```yaml
depends_on:
  db:
    condition: service_healthy
```

これは、dbが正常な状態になってからwebを起動するための設定です。

やまッチでは、webの起動時に `rails db:prepare` を実行しています。

そのため、PostgreSQLがまだ接続できない状態で処理が始まると失敗する可能性があります。

`healthcheck` と `depends_on` を組み合わせることで、この問題を防ぎやすくしています。

# 8. Dockerの起動の流れ

`docker compose up --build` を実行した場合、主に以下の流れで起動します。

1. `compose.yaml` を読み込む
2. Dockerイメージを準備する
3. dbコンテナを起動する
4. PostgreSQLの状態を確認する
5. webコンテナを起動する
6. GemやYarnの依存関係、DBを準備する
7. `./bin/dev` で開発用プロセスを起動する

また、`ports` には以下の設定があります。

```yaml
ports:
  - "3000:3000"
```

これはMac側の3000番ポートを、コンテナ側の3000番ポートに接続する設定です。

そのため、Railsが適切なアドレスで待ち受けていれば、ブラウザから `localhost:3000` でアクセスできます。

# 9. Dockerの基本コマンド

普段使用しているコマンドも整理します。

| コマンド | 役割 |
| --- | --- |
| docker compose up | コンテナの作成・起動 |
| docker compose up --build | ビルドしてから起動 |
| docker compose build | イメージのビルド |
| docker compose stop | コンテナの停止 |
| docker compose down | コンテナの停止・削除 |
| docker compose down -v | コンテナと対象Volumeの削除 |
| docker compose ps | コンテナの状態確認 |
| docker image ls | イメージの一覧表示 |
| docker volume ls | Volumeの一覧表示 |

特に注意したいのは `down` と `down -v` の違いです。

`down` では名前付きVolumeは通常残りますが、`down -v` ではComposeで定義した名前付きVolumeなども削除されます。

DBのデータも失われる可能性があるため、安易に実行しないようにしたいと思います。

# 10. まとめ

これまではDockerを開発環境を起動するためのものとして使用していましたが、今回調べたことで、イメージ・コンテナ・Volumeがそれぞれ異なる役割を持っていることが分かりました。

特に、Dockerfileでイメージを作り、Docker Composeでサービスを管理し、Volumeでデータを保持するという関係が整理できました。

まだ細かな仕組みまで理解できているわけではありませんが、普段何となく使用していたコマンドや設定が、何のために必要なのかを以前より理解できたと思います。

今後は、Dockerfileの改善やPostgreSQLのバージョン固定、Volumeの保存先なども確認していきたいと思います。
