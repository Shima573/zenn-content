## はじめに

Railsでのデータ取得やデータベースの仕組みを復習する中で、N+1問題とIndexについて学習しました。

どちらもパフォーマンスに関係するものですが、それぞれ役割が異なります。

今回は、自作アプリ「やまッチ」の登山プラン機能を例に、N+1問題が発生する仕組みや対策、Indexの役割についてまとめます。

## N+1問題とは

N+1問題とは、複数のデータを取得した後、それぞれに関連するデータを個別に取得することで、SQLの発行回数が増え、パフォーマンスが低下する問題です。

例えば、10件のデータを取得した後、それぞれに関連するデータを1件ずつ取得すると、

- 最初のデータ取得：1回
- 関連データの取得：10回

合計11回のSQLが発行されます。

データが増えるほどSQLの発行回数も増えるため、処理が遅くなる原因になります。

## 自作アプリで考えてみる

自作アプリ「やまッチ」には、登山プラン（Plan）と山（Mountain）のモデルがあります。

PlanはMountainに関連付けられており、登山プランから山の情報を取得できます。

例えば、登山プラン一覧画面でプラン名と山の名前を表示する場合を考えます。

**app/controllers/plans_controller.rb（説明用の例）**

```ruby
@plans = current_user.plans
```

このコードでは、ログイン中のユーザーに紐づく登山プランを取得するための準備をしています。

Railsには、実際にデータが必要になるまでSQLを実行しない「遅延実行」という仕組みがあり、今回の場合は通常、Viewでデータを使用するタイミングでSQLが発行されます。

続いて、Viewでプラン名と山の名前を表示します。

**app/views/plans/index.html.erb（説明用の例）**

```erb
<% @plans.each do |plan| %>
  <p><%= plan.title %></p>
  <p><%= plan.mountain.name %></p>
<% end %>
```

ここで注目したいのが、`plan.mountain.name` です。

このコードは、プランに関連付けられた山の名前を取得しています。

しかし、山のデータを事前に読み込んでいない場合、プランごとにSQLが発行されます。

### 発行されるSQLの例

仮に登山プランが3件あり、それぞれ異なる山に紐づいている場合、キャッシュなどが効いていなければ、以下のようなSQLが発行されます。

```sql
-- 登山プランを取得（1回）
SELECT * FROM plans WHERE user_id = 1;

-- 各プランに関連する山を取得（3回）
SELECT * FROM mountains WHERE id = 1;
SELECT * FROM mountains WHERE id = 2;
SELECT * FROM mountains WHERE id = 3;
```

最初のプラン取得で1回、関連する山の取得で3回、合計4回のSQLが発行されています。

つまり、登山プランが100件になれば、同じ条件では101回のSQLが発行される可能性があります。

これがN+1問題です。

※ 上記は仕組みを理解するための例であり、実際のアプリでN+1問題が発生していることを確認した結果ではありません。

## N+1問題を解決するには？

Railsでは、`includes` を使って関連するデータを事前にまとめて取得する方法があります。

**app/controllers/plans_controller.rb（改善例）**

```ruby
@plans = current_user.plans.includes(:mountain)
```

`includes(:mountain)` を指定すると、プランに関連する山の情報をあらかじめ読み込めます。

このような読み込み方法を**Eager Loading（事前読み込み）**と呼びます。

プランごとに山の情報を取得するのではなく、必要な山の情報をまとめて取得することで、SQLの発行回数を抑えられます。

今回の例では、通常、次のようなSQLが発行されます。

```sql
-- 登山プランを取得
SELECT * FROM plans WHERE user_id = 1;

-- 関連する山をまとめて取得
SELECT * FROM mountains
WHERE id IN (1, 2, 3);
```

先ほどは4回発行されていたSQLが、2回に減りました。

`includes` は条件によってJOINを使う場合もありますが、今回のようなケースでは、関連データをまとめて取得することでSQLの発行回数を抑えられます。

### N+1問題についてのまとめ

今回の学習で、N+1問題は単純にデータが多いことではなく、関連データを取得する際にSQLが繰り返し発行されることが問題だと理解しました。

RailsではAssociationを使って簡単に関連データを取得できますが、その裏側でどのようなSQLが発行されているかを意識することも重要です。

## Indexとは？

Indexとは、データベース内のデータを効率よく検索するための仕組みです。

本の巻末にある索引をイメージすると分かりやすいです。

例えば、1,000ページある本から「PostgreSQL」という単語を探す場合を考えます。

- **索引がない場合**：最初からページをめくって探す。
- **索引がある場合**：索引で「PostgreSQL」が載っているページを確認し、目的のページに移動する。

![インデックス検索の仕組み比較](/images/インデックス検索の仕組み比較.png)

データベースでも似たような仕組みが使われています。

ただし、Indexがあれば必ず速くなるわけではありません。

検索条件やデータ件数によっては、Indexを使わずに検索した方が効率的な場合もあります。

## 自作アプリで考えてみる

例えば、登山プラン一覧を取得する処理を考えてみましょう。

**app/controllers/plans_controller.rb（説明用の例）**

```ruby
@plans = current_user.plans
```

このコードでは、ログイン中のユーザーに関連するプランを取得するための準備をしています。

実際にデータが必要になった際に発行されるSQLは、概ね次のようになります。

```sql
SELECT * FROM plans
WHERE user_id = 1;
```

ここで注目したいのが、

```sql
WHERE user_id = 1
```

です。

これは、`plans` テーブルの中から `user_id` が `1` のデータを探すという意味です。

もし大量のプランが登録されていた場合、Indexがなければ、多くの行を調べる必要が生じる可能性があります。

PostgreSQLでは、テーブルを順番に読み取る方法を `Seq Scan` と呼びます。

一方、`user_id` にIndexが設定されていれば、`Index Scan` などを利用して、目的のデータを効率よく探せる可能性があります。

ただし、Indexが存在していても、PostgreSQLが必ず使用するわけではありません。

## add_indexとは？

Railsでは、マイグレーションファイルで `add_index` を使ってIndexを追加できます。

**db/migrate/xxxxxxxxxxxxxx_add_index_to_plans.rb（説明用の例）**

```ruby
add_index :plans, :user_id
```

それぞれの意味は、

- `add_index`：Indexを追加するRailsのメソッド
- `:plans`：対象のテーブル
- `:user_id`：Indexを作成するカラム

です。

つまり、`plans` テーブルの `user_id` にIndexを作成するという意味です。

また、Railsのマイグレーションでは、次のような書き方もあります。

```ruby
t.references :user, null: false, foreign_key: true
```

Railsでは、`t.references` によって通常はIndexも自動で作成されます。

なお、`foreign_key: true` は外部キー制約の設定であり、Indexとは役割が異なります。

### Indexが設定されているか確認する方法

自作アプリの `schema.rb` を確認すると、`plans` テーブルには次のIndexが設定されています。

**db/schema.rb**

```ruby
t.index ["mountain_id"], name: "index_plans_on_mountain_id"
t.index ["user_id"], name: "index_plans_on_user_id"
```

これは、`mountain_id` と `user_id` にそれぞれIndexが設定されていることを表しています。

実際のアプリでは、ユーザーに紐づく登山プランを取得する処理があるため、`user_id` はIndexを利用する候補となるカラムです。

## Indexは何でも設定すればよい？

Indexを設定すると検索が高速になる可能性がありますが、デメリットもあります。

| メリット | デメリット |
|---|---|
| 検索や絞り込みを高速化できる | Indexを保存する容量が必要 |
| JOINの効率改善に役立つ | データの追加・更新・削除時にIndexの更新処理が発生する |

そのため、すべてのカラムにIndexを設定すればよいわけではありません。

よく検索条件に使うカラムや、関連付けに使うカラムなどを中心に検討するのが基本です。

また、実際にIndexが使用されているかは、PostgreSQLの `EXPLAIN` などを使って実行計画を確認できます。

## N+1問題とIndexの違い

ここまで理解すると、N+1問題とIndexの違いも見えてきます。

| | N+1問題 | Index |
|---|---|---|
| 着目点 | SQLの発行回数 | データの検索効率 |
| 問題 | SQLが大量に発行される | データ検索に時間がかかる |
| 対策例 | `includes` | `add_index` |

つまり、

- **N+1問題**：SQLを何回発行しているか。
- **Index**：SQLの中でどれだけ効率よくデータを探せるか。

という違いがあります。

どちらもパフォーマンスに関係しますが、改善する部分が異なります。

## まとめ

今回は、RailsのN+1問題とデータベースのIndexについて、自作アプリのコードを例に学習しました。
N+1問題は、関連データを取得する際にSQLの発行回数が増える問題であり、`includes` などを使って改善できます。

一方、Indexはデータベース内の検索を効率化する仕組みです。
N+1問題はSQLの発行回数、Indexはデータの検索効率に着目しているという違いがあります。
RailsではAssociationを使って簡単にデータを取得できますが、実際にどのようなSQLが発行され、データベースがどのようにデータを探しているのかを意識することが重要だと理解しました。
