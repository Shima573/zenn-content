## はじめに

普段の開発では、`git add` や `git commit`、`git push` などのコマンドを使用しています。

しかし、それぞれのコマンドが内部でどのような役割を持ち、GitとGitHubがどのように連携しているのか、改めて整理してみることにしました。

今回は、自作アプリ「やまッチ」での開発を例に、GitとGitHubの基本的な仕組みや操作についてまとめます。

## GitとGitHubとは？

### Gitとは？

Gitは、ファイルの変更履歴を記録・管理するためのバージョン管理システムです。

例えば、自作アプリ「やまッチ」の開発中に、

- 新しい機能を追加した
- 既存のコードを修正した
- 修正後に不具合が発生した

ということがあったとします。

Gitを使うと、いつ・どのような変更を記録したのか確認したり、過去の状態を参照したりできます。

つまり、コードの変更履歴を管理する役割があります。

### GitHubとは？

GitHubは、Gitで管理しているリポジトリをオンライン上で共有・管理できるサービスです。

GitHubを使うことで、コードの共有だけでなく、Pull RequestによるレビューやIssueによるタスク管理などもできます。

### GitとGitHubの違い

| 項目 | Git | GitHub |
|---|---|---|
| 役割 | 変更履歴の管理 | コードの共有・共同開発 |
| 利用場所 | ローカル環境など | オンライン |
| 主な機能 | commit、branch、merge | Pull Request、Issue、レビュー |
| ネット接続 | 基本操作は不要 | 通信が必要 |

重要なのは、**GitとGitHubは別のもの**という点です。

GitHubを利用しなくても、Gitだけで変更履歴を管理できます。

## Gitの基本構造

Gitで変更内容を記録し、GitHubへ反映するまでには、主に次の4つの場所が関係します。

![Gitの基本構造と操作フロー](/images/Gitの基本構造と操作フロー.png)

それぞれの役割を整理します。

### 1. ワークツリー

VSCodeなどで実際にファイルを編集する場所です。

例えば、`app/controllers/plans_controller.rb` を修正した場合、その変更はまずワークツリーに存在します。

### 2. ステージングエリア

次のコミットに含めたい変更を選択して準備する場所です。

```bash
git add app/controllers/plans_controller.rb
```

このコマンドで、指定したファイルの現在の変更内容をステージングします。

なお、`git add` を実行した後に同じファイルを再編集した場合、その追加の変更をコミットに含めるには、基本的にもう一度 `git add` が必要です。

### 3. ローカルリポジトリ

コミットによって変更履歴を記録する場所です。

```bash
git commit -m "登山プランの処理を修正"
```

ステージングした変更をコミットすることで、変更履歴として記録されます。

ここまでの操作は、GitHubに接続しなくても実行できます。

### 4. リモートリポジトリ

GitHubなどで変更履歴を共有・管理する場所です。

例えば、次のコマンドを実行します。

```bash
git push origin main
```

これにより、ローカルの `main` ブランチのコミットをリモートリポジトリへ送信できます。

ここまでを整理すると、普段何気なく実行している、

```bash
git add
git commit
git push
```

は、それぞれ異なる役割を持っています。

- `add`：次のコミットに含める変更を準備する
- `commit`：ステージングした変更を履歴として記録する
- `push`：コミットをリモートリポジトリへ送る

特に、**commitしただけではGitHubに反映されない**という点が重要です。

## リポジトリとは？

リポジトリ（Repository）とは、ファイルや変更履歴を管理するための場所です。

Gitでは、主にローカルリポジトリとリモートリポジトリを使用します。

### ローカルリポジトリとリモートリポジトリ

| 種類 | 役割 |
|---|---|
| ローカルリポジトリ | 自分のPC上で変更履歴を管理する |
| リモートリポジトリ | GitHubなどで変更履歴を共有・管理する |

例えば「やまッチ」の場合、

- 自分のPCにある `yamatch` のGitリポジトリ
- GitHub上にある `yamatch` のリポジトリ

がそれぞれ存在します。

この2つは別々に管理されているため、ローカルでコミットしても、GitHubには自動で反映されません。

そこで `git push` を使い、ローカルで記録したコミットをリモートへ送信します。

## cloneとは？

`clone` は、既存のリポジトリを複製する操作です。

例えば、GitHub上にある「やまッチ」のリポジトリを自分のPCに取得する場合です。

```bash
git clone https://github.com/ユーザー名/yamatch.git
```

実行すると、基本的に次のものが取得・設定されます。

- アプリのファイル
- コミット履歴
- ブランチに関する情報
- リモートリポジトリの接続設定

ここで重要なのは、**cloneは単にファイルをダウンロードするだけではない**という点です。

Gitの変更履歴も取得するため、clone後も継続してGitで開発できます。

また、GitHubなどからcloneした場合、通常は取得元のリモートリポジトリが `origin` という名前で登録されます。

## originとorigin/mainの違い

Gitのコマンドでよく登場する `origin` と `origin/main` ですが、それぞれ異なる意味を持っています。

### originとは？

`origin` は、リモートリポジトリに付けられた名前です。

例えば、次のコマンドです。

```bash
git push origin main
```

この場合、

- `origin`：送信先のリモートリポジトリ
- `main`：送信するローカルブランチ

を表しています。

なお、`origin` はGitで必ず使用しなければならない固定名ではなく、別の名前に変更することもできます。

### origin/mainとは？

`origin/main` は、リモートの `main` ブランチの状態をローカルで記録している**リモート追跡ブランチ**です。

| 名前 | 役割 |
|---|---|
| `main` | ローカルのmainブランチ |
| `origin` | リモートリポジトリの名前 |
| `origin/main` | リモートのmainの状態をローカルで記録する参照 |

例えば、次のコマンドを実行します。

```bash
git fetch origin
```

すると、GitHub上の新しいコミット情報などが取得され、通常は `origin/main` も更新されます。

ただし、ローカルの `main` が自動的に更新されるわけではありません。

つまり、**`main` と `origin/main` は別々に管理されている**ということです。

また、`origin/main` はGitHub上の状態を常に直接参照しているわけではなく、最後に取得した情報を保持しています。

そのため、最新の情報を確認するには `fetch` などで更新する必要があります。

## ブランチとは？

ブランチ（Branch）とは、変更履歴を分岐させて、別々の作業を進めるための仕組みです。

例えば「やまッチ」で、新しく登山プラン機能を追加するとします。

そのとき、`main` ブランチで直接作業するのではなく、別のブランチを作成します。

![Gitのブランチ分岐と統合フロー図](/images/Gitのブランチ分岐と統合フロー図.png)

この図では、

- `main`：基本となるブランチ
- `feature/add-plans`：登山プラン機能を開発するブランチ

を表しています。

ブランチを分けることで、`main` に直接変更を加えずに新機能の開発を進められます。

### ブランチを使う理由

ブランチを使う理由は、**変更を分けて管理し、複数の作業を並行して進められるようにするため**です。

例えば、登山プラン機能と登山記録機能を別々のブランチで開発すれば、それぞれの変更を独立して管理できます。

### ブランチの基本操作

**新しいブランチを作成して切り替える**

```bash
git switch -c feature/add-plans
```

`-c` は、新しいブランチを作成するオプションです。

**現在のブランチを確認する**

```bash
git branch
```

**ブランチを切り替える**

```bash
git switch main
```

ここで覚えておきたいのは、**ブランチはフォルダを丸ごとコピーする仕組みではない**ということです。

Gitはコミットのつながりを管理しており、ブランチは基本的に特定のコミットを指しています。

### switchとcheckoutの違い

Gitでブランチを切り替える方法には、`switch` と `checkout` があります。

以前は主に `checkout` が使われていましたが、Git 2.23から `switch` が追加されました。

`checkout` はブランチの切り替えだけでなく、ファイルを指定した状態に戻す操作などにも使われるコマンドです。

そのため、役割を分かりやすくする目的で、ブランチ操作に特化した `switch` と、ファイルの復元に使う `restore` が追加されました。

| 操作 | checkout | switch / restore |
|---|---|---|
| ブランチの切り替え | `git checkout main` | `git switch main` |
| ブランチの作成と切り替え | `git checkout -b feature/test` | `git switch -c feature/test` |
| ファイルの変更を破棄 | `git checkout -- file.rb` | `git restore file.rb` |

例えば、`main` ブランチに切り替える場合は、次のどちらでも実行できます。

```bash
git checkout main
```

```bash
git switch main
```

どちらも同じようにブランチを切り替えられますが、用途が明確な `switch` を使うと、操作の意図が分かりやすくなります。

なお、`checkout` が使えなくなったわけではありません。

現在も利用できるため、参考記事で `checkout` が登場しても、用途を理解していれば読み替えられます。

ただし、ファイルの変更を破棄する操作は、未コミットの変更が失われる可能性があるため注意が必要です。

## mergeとは？

`merge` は、別のブランチで行った変更を、現在のブランチに統合する操作です。

例えば、`feature/add-plans` で登山プラン機能が完成したとします。

その変更を `main` に取り込みたい場合、次のように操作できます。

```bash
git switch main
git merge feature/add-plans
```

これによって、ローカルの `feature/add-plans` の変更をローカルの `main` に取り込めます。

ただし、別々のブランチで同じ箇所を変更した場合など、Gitが変更内容を自動で統合できないことがあります。

これを**コンフリクト（競合）**と呼びます。

なお、mergeは必ず新しいコミットを作成するわけではありません。

ブランチの履歴によっては、参照先を進めるだけで統合できる場合もあります。これをFast-forwardと呼びます。

## fetchとpullとは？

`git fetch`（フェッチ）と `git pull`（プル）は、どちらもリモートリポジトリから更新情報を取得するためのGitコマンドです。

では、何が異なるのでしょうか。

### fetchとは？

`fetch` は、**リモートリポジトリの変更情報を取得するコマンド**です。

```bash
git fetch origin
```

リモートリポジトリから新しいコミットやブランチの情報などを取得し、`origin/main` などのリモート追跡ブランチを更新します。

ただし、取得した変更は現在作業しているローカルブランチには自動的に統合されません。

そのため、作業中のファイルを変更せずに、リモート側の更新情報を確認できます。

### pullとは？

`pull` は、**リモートリポジトリから変更を取得し、現在のローカルブランチに取り込むコマンド**です。

```bash
git pull origin main
```

この場合、リモートの `main` ブランチから変更を取得し、現在作業しているローカルブランチに取り込みます。

例えば、現在のブランチが `feature/add-plans` の場合は、そのブランチにリモートの `main` の変更が取り込まれます。

`main` に自動的に切り替わるわけではありません。

基本的には、次の2つの操作をまとめて行うイメージです。

1. `git fetch`：リモートの変更を取得する
2. `git merge`：取得した変更を現在のブランチに統合する

ただし、Gitの設定やオプションによっては、`merge` の代わりに `rebase` が使われることもあります。

また、変更内容によってはコンフリクトが発生したり、統合方法の指定が必要になったりする場合があります。

### fetchとpullの違い

| 項目 | git fetch | git pull |
|---|---|---|
| 主な処理 | 変更情報を取得する | 変更情報を取得して取り込む |
| ローカルブランチ | 自動的には変更しない | 更新される場合がある |
| 作業ファイルへの影響 | なし | 変更される場合がある |
| 内部での処理 | 取得のみ | fetch + merge または rebaseなど |
| 使いどき | 変更内容を確認してから取り込みたいとき | リモートの変更をすぐに取り込みたいとき |

つまり、**`fetch` は変更を取得するだけ、`pull` は取得した変更を取り込むところまで行う**という違いがあります。

## Pull Requestとは？

Pull Request（PR）とは、自分が行った変更を別のブランチに取り込むよう提案するGitHubの機能です。

例えば「やまッチ」で登山プラン機能を追加した場合、

1. `feature/add-plans` で機能を開発する。
2. 変更をコミットする。
3. GitHubにpushする。
4. `main` に向けてPull Requestを作成する。
5. 変更内容を確認してmergeする。

という流れになります。

Pull Requestでは、変更したファイルやコードの差分を確認でき、コメントやレビューも行えます。

なお、**mergeはGitの機能、Pull RequestはGitHubの機能**です。

ここは混同しやすいので押さえておきたい点です。

## 自作アプリでの開発の流れ

ここまで学んだGitの基本操作を、自作アプリ「やまッチ」での開発を例に整理します。

今回は、新しく登山プラン機能を追加する場合を考えます。

### 1. mainブランチを最新にする

まず、作業の基準となる `main` ブランチへ切り替えます。

```bash
git switch main
```

次に、GitHub上の最新の変更を取り込みます。

```bash
git pull origin main
```

これにより、ローカルの `main` にリモートの変更を取り込めます。

### 2. 作業用ブランチを作成する

新しい機能を開発するために、作業用ブランチを作成します。

```bash
git switch -c feature/add-plans
```

これにより、現在の `main` を起点として `feature/add-plans` ブランチが作成され、同時に切り替わります。

ブランチを分けることで、`main` に直接変更を加えずに開発を進められます。

### 3. コードを修正する

VSCodeなどで登山プラン機能を実装します。

実装後は、次のコマンドで変更状況を確認します。

```bash
git status
```

`git status` では、変更されたファイルやステージング済みのファイル、現在のブランチなどを確認できます。

また、変更内容の差分を確認したい場合は、次のコマンドを使います。

```bash
git diff
```

`git diff` では、基本的にステージング前の変更内容を確認できます。

ステージング済みの変更内容を確認する場合は、次のコマンドを使用します。

```bash
git diff --staged
```

### 4. 変更をコミットする

変更内容を確認したら、次のコミットに含めたいファイルをステージングします。

```bash
git add app/controllers/plans_controller.rb
```

必要なファイルを追加したら、コミットします。

```bash
git commit -m "登山プラン機能を追加"
```

これにより、ステージングした変更がローカルリポジトリの履歴として記録されます。

なお、コミットしただけではGitHubには反映されません。

### 5. GitHubへpushする

ローカルで記録したコミットをGitHubへ送信します。

```bash
git push -u origin feature/add-plans
```

`-u` は、ローカルブランチとリモート側のブランチの追跡関係を設定するオプションです。

これにより、以降の `push` や `pull` でリモートやブランチの指定を省略しやすくなります。

### 6. Pull Requestを作成する

GitHub上で `feature/add-plans` から `main` に向けてPull Requestを作成します。

Pull Requestでは、変更内容やコードの差分を確認できます。

問題がなければ、GitHub上でmergeして `main` に変更を取り込みます。

### 7. ローカルのmainを更新する

GitHub上でmergeしても、ローカルの `main` は自動的には更新されません。

そのため、次のコマンドを実行します。

```bash
git switch main
git pull origin main
```

これで、GitHub上で統合した変更をローカルの `main` に取り込めます。

必要に応じて、作業が完了したブランチを削除します。

```bash
git branch -d feature/add-plans
```

このコマンドはローカルブランチを削除する操作です。リモート側のブランチは削除されません。

このように、Gitではブランチを分けて開発し、コミットで変更履歴を残しながら、GitHubのPull Requestを使って変更を統合できます。

## まとめ

今回は、GitとGitHubの違いから、基本構造やブランチの仕組み、普段の開発で使用するコマンドについて整理しました。

特に重要だと感じたのは、次の点です。

- GitとGitHubは別のものであり、Gitだけでも変更履歴を管理できる。
- `add`・`commit`・`push` はそれぞれ異なる役割を持つ。
- ブランチを使うことで、変更を分けて開発できる。
- `fetch` は変更情報の取得、`pull` は取得と取り込みを行う。
- ローカルリポジトリとリモートリポジトリは別々に管理されている。
- Pull Requestを使うことで、変更内容を確認してから別のブランチへ統合できる。

これまでは何気なく実行していたコマンドも、それぞれの役割や処理の流れを理解することで、何を操作しているのか整理できました。

今後も実際の開発でGitを使いながら、理解を深めていきたいと思います。
