## はじめに

Railsでアプリケーションを開発している中で、Controllerの`create`アクションからデータを保存する処理を書く機会がありました。

実装自体はできていたものの、`save`を実行してからデータベースに保存されるまでに、どのような処理が行われているのかをうまく説明できないことに気づきました。

そこで今回は、自作アプリの登山プラン作成機能を例に、Controllerがリクエストを受け取ってからデータベースに保存されるまでの流れを改めて整理します。

## PlansController#create
`create`アクションは、新しいデータを作成し、データベースへの保存を行う際に使用します。

今回の登山プラン作成機能では、フォームから送信された情報を受け取り、新しいPlanを作成して保存しています。

実際の`create`アクションを見ていきます。
```ruby
def create
  @mountain = Mountain.find(params[:mountain_id])
  @plan = current_user.plans.new(plan_params)

  @plan.mountain = @mountain

  if @plan.save
    redirect_to plans_path, notice: "登山プランを作成しました"
  else
    render :new, status: :see_other
  end
end
```

## Mountainを取得する
```
@mountain = Mountain.find(params[:mountain_id])
```
`mountain_id`を使ってDBからMountainを探し、取得したMountainを`@mountain`に代入しています。
では、この`mountain_id`はどこから来たのでしょうか？
`params[:mountain_id]`の値は、リクエストされたURLから取得されています。

登山プランを作成すると、例えば`POST /mountains/5/plans`へリクエストが送られます。
Railsは、このリクエストを定義されているルーティングと照らし合わせます。

そのため、RailsはURLの5をmountain_idとして扱います。
![リクエストからMountainを取得するまでの流れ](/images/mountain-find-flow.png)
そしてControllerでは、
```
Mountain.find(params[:mountain_id])
```
としているため、
```
params[:mountain_id]
↓
"5"
↓
Mountain.find("5")
↓
idが5のMountainをDBから取得
↓
取得したMountainを@mountainに代入
```
という流れになります。
つまり、「URLから取得したmountain_idを使って対象のMountainをDBから探し、取得したMountainを@mountainに代入している」という処理になります。

## paramsとStrong Parameters
`create`アクションでは、フォームやURLなどから受け取ったパラメータを使用して新しいPlanを作成します。

Railsでは、受け取ったパラメータをそのまま使用するのではなく、必要なものを選んで使用します。
### paramsとは
`params`は、HTTPリクエストからRailsが受け取ったパラメータを扱うためのものです。
先ほどのMountainを取得する処理では、URLから受け取った`mountain_id`を以下のように取得していました。
```ruby
params[:mountain_id]
```
### Strong Parametersとは
Strong Parametersは、受け取ったパラメータの中から、データの作成や更新に使用してよい項目を指定するための仕組みです。

今回の登山プランでは、以下のようにplan_paramsを定義しています。
```ruby
def plan_params
  params.require(:plan).permit(
    :title,
    :climbing_date,
    :companion_count,
    :route,
    :note,
    equipment: [],
  )
end
```
`require(:plan)`で`plan`というまとまりのパラメータを対象とし、permitでPlanの作成・更新に使用してよい項目を指定しています。
そのため、`plan_params`では、受け取ったパラメータの中からPlanの作成・更新に使用してよい項目だけを扱えるようになります。


## Planオブジェクトを作成する
```
@plan = current_user.plans.new(plan_params)
```
この処理を分解して解説していきます。
- `current_user`
  - 現在ログインしているユーザーを取得する
- `.plans`
  - ログインユーザーに紐づくPlanを扱う
- `.new(plan_params)`
  - `plan_params`の内容を使って新しいPlanオブジェクトを作成する
- `@plan`
  - 作成したPlanオブジェクトを代入する

`new`はPlanオブジェクトを作成するだけなので、この時点ではDBへの保存は行われません。
一文で表すと、
**現在のログインユーザーに紐づく新しいPlanオブジェクトを、`plan_params`で許可されたパラメータを使って作る。ただし、まだDBには保存しない。**

## MountainとPlanを関連付ける
```ruby
@plan.mountain = @mountain
```
**このPlanは、さっきURLから特定したMountainのPlanですよ**
という関連付けを行っています。

ここで一つ大事なのは、**`mountain_id`を`plan_params`に含めていない理由**も見えてくることです。

フォームから「どの山にするか」を自由に送って決めるのではなく、**山の詳細から遷移したURLの`:mountain_id`を使って対象のMountainを特定し、Controller側でPlanに関連付けている**わけです。

## Planを保存する

```ruby
if @plan.save
  redirect_to plans_path, notice: "登山プランを作成しました"
else
  render :new, status: :see_other
end
```

### なぜsaveをifの条件にしているのか？
ポイントは、saveが単に保存処理を行うだけではなく、保存できたかどうかを真偽値（true / false）で返すことです。
saveはデータの保存を試み、保存に成功した場合はtrue、失敗した場合はfalseを返します。
- 保存に成功した場合： true を返す
- バリデーションエラーなどで失敗した場合： false を返す

### では、saveを実行すると何が起こる？
saveを実行すると、まずModelに定義されたバリデーションが実行されます。
バリデーションに問題がなく保存に成功するとtrue、保存に失敗するとfalseが返され、その戻り値によってifの処理が分岐します。
![saveからPlanがDBに保存されるまでの流れ](/images/plan-save-flow.png)

### Active Recordを通してDBへ保存する

バリデーションに問題がなければ、DBへの保存処理に進みます。

Railsでは、`save`などの操作とデータベースとのやり取りをActive Recordが担っています。

今回のように新しいPlanを保存する場合、Active Recordを通してデータを追加するためのSQLが実行されます。

```text
@plan.save
↓
バリデーションを通過
↓
Active Record
↓
INSERT文
↓
PostgreSQL
↓
plansテーブルにデータが保存される
```

### SQLとPostgreSQL

SQLは、データベースに対して「データを追加する」「取得する」「更新する」「削除する」といった操作を指示するための言語です。

今回のように新しいPlanを追加する場合は、`INSERT`が使用されます。

一方、PostgreSQLはSQLを受け取り、実際にデータを管理するデータベース管理システムです。

### 保存に成功した場合

`save`が`true`を返すと、`redirect_to`によって指定したパスへリダイレクトします。
```ruby
redirect_to plans_path, notice: "登山プランを作成しました"
```

### 保存に失敗した場合

`save`が`false`を返すと、以下の処理が実行されます。

```ruby
render :new, status: :see_other
```
`redirect_to`とは異なり、`new`アクションへ移動するわけではなく、`create`アクションの処理の中で`new`のテンプレートを表示しています。
## まとめ
今回整理してみて、これまで何となく使用していたparams、new、saveが、それぞれ別の役割を持っていることが分かりました。

特に、newの時点ではまだDBには保存されておらず、saveを実行するとバリデーションが行われ、問題がなければActive Recordを通してSQLが実行され、DBに保存されるという流れを理解できました。
