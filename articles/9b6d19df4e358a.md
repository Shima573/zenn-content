## データベースとは
データベース（DB）とは、必要な情報を利用しやすい形で整理して保存した「データの集まり」です。

今回の「やまッチ」で考えると、例えば、
```
データベース
│
├── users
│   └── ユーザー情報
│
├── mountains
│   └── 山の情報
│
├── plans
│   └── 登山プラン
│
└── favorites
    └── お気に入り情報
```
のように、アプリで必要なデータを保存しています。
そして重要なのは保存するだけではないところです。
例えば、

```
Plan.all
```

ならPlanを取得したり、

```
Plan.find(1)
```

なら特定のPlanを探したり、

```
plan.update(...)
```

なら保存されているPlanを更新したりします。

データベースは単にデータを保存するだけでなく、そのデータをアプリケーションから検索・追加・更新・削除して利用します。
では、こうしたデータベースを管理しているものは何なのでしょうか。

## DB・DBMS・PostgreSQLはそれぞれ何が違うのか？
DB（データベース）、DBMS（データベース管理システム）、PostgreSQL（ポスグレ）は、
それぞれ抽象度（レイヤー）が異なる概念です。関係性を一言で表すと以下のようになります。
- DB: 保存されている「データの集まり（箱・データそのもの）」
- DBMS: DBを整理・操作・管理する「ソフトウェアの種類（仕組み）」
- PostgreSQL: DBMSという種類に含まれる「具体的な製品（ソフトウェア）」

関係性を整理すると、以下のようになります。
![図書館で学ぶDB・DBMS・PostgreSQL](/images/図書館で学ぶDB・DBMS・PostgreSQL.png)

### 他にはどんなDBMSがあるのか

PostgreSQL以外にも、さまざまなDBMSがあります。

その中でもPostgreSQLやMySQL、SQLiteは、RDBMSと呼ばれる種類に分類されます。

正式名称は Relational Database Management System（リレーショナル・データベース・マネジメント・システム） で、
日本語では「リレーショナルデータベース管理システム」と呼ばれます。

代表的なものを調べてみると、データの管理方法によってRDBMSやNoSQLなどに分類されることが分かりました。

#### 代表的なRDBMSの違い

RDBMSにはPostgreSQL以外にもさまざまな種類があります。

これまでPostgreSQLを使用してきましたが、MySQLやSQLiteなどとは何が違うのか気になったため、それぞれの仕組みや特徴について調べてみました。

| DBMS | 主な特徴 | 主な利用例 |
| --- | --- | --- |
| PostgreSQL | 機能が豊富で、JSONや位置情報などさまざまなデータを扱える | Webアプリ、業務システムなど |
| MySQL | Webサービスで広く利用されており、利用実績や情報が豊富 | Webサイト、Webアプリなど |
| SQLite | DBサーバーが不要で、基本的に1つのファイルでデータを管理できる | 小規模アプリ、モバイルアプリ、開発・テスト環境など |
| Oracle Database | 大規模なシステム向けの機能を多く備えている | 企業の基幹システムなど |
| Microsoft SQL Server | Microsoft製で、Microsoft製品との連携に強みを持つ | 企業・業務システムなど |

また、調べていて大きな違いだと感じたのが、DBMSの利用方式です。
PostgreSQLやMySQLなどは、DBサーバーを動かし、アプリケーションからそのサーバーへ接続して利用する「クライアント・サーバー型」です。
一方、SQLiteは独立したDBサーバーを必要とせず、アプリケーションに組み込んでデータベースを扱う「組み込み型」です。

#### RDBMS以外のDBMS

DBMSにはRDBMSだけでなく、NoSQLと呼ばれるものもあります。

| DBMS | 種類 | 特徴 |
| --- | --- | --- |
| MongoDB | ドキュメント型 | JSONに近い形式でデータを扱い、柔軟なデータ構造を持てる |
| Redis | キーバリュー型 | 主にメモリ上でデータを扱い、高速な読み書きに利用される |


- 今回の「やまッチ」ではPostgreSQLを使用しています。

PostgreSQLの機能を他のDBMSと比較して選んだわけではなく、アプリをデプロイする際にRenderとNeonを利用する構成を採用したことがきっかけでした。

NeonはPostgreSQLを提供するサービスのため、この構成に合わせてPostgreSQLを使用しています。

### そもそもRDBMSの「リレーショナル」とは何なのか？

RDBMSでは、データを行と列からなるテーブル形式で管理します。
また、主キーや外部キーを利用することで、複数のテーブルに分けたデータを関連付けて扱うことができます。

例えば「やまッチ」では、ユーザー情報を`users`テーブル、登山プランを`plans`テーブルに分けて保存しています。

`plans`テーブルが持つ`user_id`によって、「どのユーザーの登山プランなのか」を関連付けることができます。

このように、データをテーブルに分け、それぞれのデータを関連付けながら管理できるのがRDBMSの特徴の一つです。

### テーブル・カラム・レコードとは

ここまで「テーブル」という言葉を使ってきましたが、
RDBMSのデータがどのような構造で保存されているのかを整理します。
![テーブル・カラム・レコード解説図](/images/テーブル・カラム・レコード解説図.png)

#### テーブル
テーブル（Table）とは、データを保存するための「表」のことです。
ExcelやGoogleスプレッドシートのような、行と列で構成された表をイメージすると分かりやすいです。
RDBMSでは、関連するデータをテーブルごとに分けて管理します。
例えば「やまッチ」では、ユーザー情報をusersテーブル、登山プランの情報をplansテーブルに保存しています。

#### カラム
カラム（Column）とは、テーブルの「列」にあたり、どのようなデータを保存するのかを表す項目です。
「やまッチ」のplansテーブルでは、user_id、mountain_id、title、climbing_dateなどがカラムにあたります。
また、それぞれのカラムにはデータ型が設定されています。
例えば、titleは文字列を扱うstring、climbing_dateは日付を扱うdate、companion_countは整数を扱うintegerとして定義されています。
`schema.rb`
```
    t.bigint "user_id", null: false
    t.bigint "mountain_id", null: false
    t.string "title"
    t.date "climbing_date", null: false
    t.integer "companion_count"
```
#### レコード

レコード（Record）とは、テーブルの「行」にあたり、1件分のデータを表します。

「やまッチ」の`plans`テーブルの場合、1つの登山プランが1つのレコードとして保存されています。

実際にRailsコンソールから`Plan.first`を実行して、保存されている最初の登山プランを取得してみます。

```ruby
Plan.first
```
取得したデータの一部を表にすると、次のようになります。
| id | user_id | mountain_id | title | climbing_date | companion_count |
| --- | --- | --- | --- | --- | --- |
| 2 | 32 | 18 | テスト登山 | 2026-09-24 | 5 |

この横1行が1つのレコードであり、1つの登山プランの情報を表しています。

## SQLとは
SQLは「Structured Query Language」の略です。

SQLは、RDBMSに対してデータの取得・追加・更新・削除などを行うための言語です。

Railsでは普段Active Recordを使っているため、基本的なデータ操作でSQLを直接記述する必要はありません。
しかし、その裏側ではActive RecordによってSQLが生成され、データベースに対して実行されています。
例えば、RailsコンソールでPlan.firstを実行すると、次のSQLが生成されました。
```
SELECT "plans".* FROM "plans" ORDER BY "plans"."id" ASC LIMIT 1
```
このSQLでは、plansテーブルのデータをidの昇順に並べ、その中から最初の1件を取得しています。

### そもそもSELECT、FROM、ORDER BY、LIMITってそれぞれ何？
簡単に表すならこんな感じに
| SQL | 意味 | 今回の場合 |
|---|---|---|
| `SELECT` | **何を取得する？** | `plans.*` → plansの全カラム |
| `FROM` | **どこから？** | `plans`テーブルから |
| `ORDER BY` | **どんな順番で？** | `id`の昇順で |
| `LIMIT` | **何件まで？** | 1件まで |

## SQLの種類
:::details DML（データ操作言語）
DML（Data Manipulation Language）は、テーブルに格納されている「データそのもの」を操作するための命令です。日常的なシステム開発やデータ分析で最も頻繁に使われます。
- SELECT: データベースから必要なデータを検索・抽出する
- INSERT: テーブルに新しいデータを追加（登録）する
- UPDATE: すでに登録されているデータを最新の状態に更新（書き換え）する
- DELETE: テーブルから不要なデータを削除する
:::
:::details DDL（データ定義言語）
DDL（Data Definition Language）は、データを格納する「器（テーブルやデータベースなどの構造）」を作成・定義・管理するための命令です。
- CREATE: 新しいデータベースやテーブルを作成する
- ALTER: 既存のテーブルの構造を変更する（列を追加する、データ型を変えるなど）
- DROP: データベースやテーブルを構造ごと完全に削除する
- TRUNCATE: テーブルの構造を残したまま、すべてのデータを削除する
:::
:::details DCL（データ制御言語）
DCL（Data Control Language）は、データベースの「安全性を保つための権限」を制御する命令です。主にデータベース管理者が使用します。
- GRANT: 特定のユーザーに対して、データの閲覧や書き込みなどの権限を与える
- REVOKE: 一度与えたユーザーの権限を剥奪（取り消し）する
:::
:::details TCL（トランザクション制御言語）
TCL（Transaction Control Language）は、複数のデータ操作をひとまとまりの処理として扱う「トランザクション」を制御する命令です。銀行の振り込み処理などで、データの整合性を守るために利用されます。
- COMMIT: 一連のデータ変更処理を確定し、データベースに反映する
- ROLLBACK: 一連のデータ変更処理を取り消し、処理前の状態に戻す
- SAVEPOINT: トランザクションの途中に保存点を設定し、必要に応じてその地点まで変更を戻せるようにする
:::

SQLにはこのようにいくつかの種類がありますが、今回はRailsで普段行っているデータの取得・追加・更新・削除との関係を理解するため、DMLを中心に見ていきます。
## SQLにはSELECT以外にどんな命令があるの？
| やりたいこと | SQL | Railsの例 |
|---|---|---|
| 取得 | `SELECT` | `Plan.first` / `Plan.find(2)` |
| 新規作成（未保存） | SQLは実行されない | `Plan.new(...)` |
| 新規データを保存 | `INSERT` | `plan.save` |
| 作成して保存 | `INSERT` | `Plan.create(...)` |
| 更新 | `UPDATE` | `plan.update(...)` |
| 削除 | `DELETE` | `plan.destroy` |

Plan.newはRuby上にオブジェクトを作成するだけなので、この時点ではSQLは実行されません。その後saveを実行すると、新規データの場合はINSERTが実行されます。
また、Plan.create(...)はオブジェクトの作成から保存までをまとめて行います。
※ saveは新規レコードの場合はINSERT、既存レコードの変更を保存する場合はUPDATEになります。

## まとめ

今回は、普段Railsで使用しているデータベースについて、DB・DBMS・SQLの関係から改めて整理しました。

これまではRailsで`Plan.find`や`Plan.create`、`plan.update`などを使ってデータを操作していましたが、その裏側ではActive RecordがSQLを生成し、PostgreSQLを通してデータベースを操作していることが分かりました。

また、DBは単にデータを保存しておくものではなく、テーブル・カラム・レコードという形でデータを整理し、SQLによって取得・追加・更新・削除して利用していることも改めて理解できました。

これまで何気なく使っていた、
Rails → Active Record → SQL → PostgreSQL → データベース
という流れを整理したことで、自分がRailsからどのようにデータベースを利用していたのかを理解することができました。
